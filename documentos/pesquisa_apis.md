Uma API ( Application Programming Interface ), é um conjunto de regras que define como um software pode pedir serviços e dados para outro software, em termo não técnicos é basicamente um facilitador, um exemplo para que haja clareza no atendimento é pensar numa API como se fosse um garçom, ela recolhe o pedido feito pelo cliente e leva para a cozinha, permite que 2 sistemas diferentes, feitos muitas vezes em linguagens diferentes consigam realizar uma comunicação entre si.

Na prática, a comunicação por meio de APIs web segue o modelo cliente-servidor. O cliente, que pode ser um site, um aplicativo de celular ou outro servidor, envia uma requisição pela internet, normalmente usando o protocolo HTTP. O servidor a recebe, verifica se o pedido é válido e se o cliente tem permissão, executa a operação necessária (consultar o banco de dados, gravar um registro, calcular algo) e devolve uma resposta. Cada requisição é independente, e o servidor não precisa “lembrar” das anteriores, o que torna o sistema mais simples de escalar. O que trafega entre as partes são mensagens de texto padronizadas, e por isso um sistema escrito em PHP consegue conversar com outro em Java, Python ou JavaScript, desde que ambos entendam HTTP e o formato dos dados. 

Entre os estilos de API, o mais usado atualmente é o REST (Representational State Transfer), proposto por Roy Fielding em sua tese de doutorado, em 2000. REST não é um protocolo nem uma biblioteca, mas um conjunto de princípios de arquitetura. Nele, tudo o que a API oferece é tratado como um recurso um cliente, um produto, um pedido, e cada recurso é identificado por uma URL. As operações sobre esses recursos são expressas pelos métodos do próprio HTTP, a comunicação é sem estado e as respostas costumam representar o recurso em um formato de texto, quase sempre JSON. Uma API que segue esses princípios é chamada de RESTful, e sua principal vantagem é a previsibilidade: quem conhece a lógica de uma API REST consegue entender outra com facilidade. 

Os métodos HTTP indicam qual ação o cliente quer realizar sobre o recurso apontado pela URL. O GET serve para consultar dados e não deve modificar nada no servidor. O POST envia dados para criar um novo recurso. O PUT substitui um recurso existente por completo, de modo que o cliente precisa enviar todos os campos. O PATCH também altera um recurso existente, mas apenas parcialmente, enviando somente os campos que mudaram. O DELETE remove o recurso. Essa correspondência lembra as quatro operações básicas de um banco de dados, criar, ler, atualizar e apagar, nosso querido CRUD, e é isso que torna o REST tão natural para sistemas que gerenciam cadastros. Vale notar que GET, PUT e DELETE são idempotentes, ou seja, repetir a mesma chamada várias vezes produz o mesmo resultado final, enquanto o POST normalmente não é, pois cada chamada pode criar um novo registro. Toda comunicação é feita por pares de requisição e resposta HTTP. A requisição é composta por uma linha inicial com o método e o caminho do recurso, pelo header que traz informações adicionais, como o formato aceito e as credenciais, e, quando necessário, pelo body com os dados enviados. A resposta traz um código de status, header e, em geral, um body com o resultado. Os códigos de status são agrupados por famílias: os iniciados em 2 indicam sucesso 200 para OK, 201 para recurso criado, 204 para sucesso sem conteúdo, os iniciados em 4 indicam erro do cliente 400 para requisição inválida, 401 para não autenticado, 403 para sem permissão, 404 para recurso não encontrado e os iniciados em 5 indicam falha no servidor como o 500. A seguir, um exemplo de requisição GET para consultar um produto e a resposta correspondente: 

GET /api/produtos/15 HTTP/1.1
Host: api.exemplo.com.br
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIs…


HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 15,
  "nome": "Teclado Mecânico",
  "preco": 249.90,
  "estoque": 32,
  "ativo": true
}

O endereço usado nessas chamadas, no caso /api/produtos/15, é chamado de endpoint. Um endpoint é a combinação de uma URL com um método HTTP e representa um ponto de acesso específico da API. Em uma API bem desenhada, as URLs usam substantivos no plural para nomear os recursos, e o método define a ação. Assim, GET /produtos lista todos os produtos, GET /produtos/15 retorna apenas o de identificador 15, POST /produtos cria um novo, PUT /produtos/15 e PATCH /produtos/15 o atualizam e DELETE /produtos/15 o exclui. Isso evita URLs como /buscarProduto ou /apagarProduto, que misturam a ação com o recurso e dificultam a padronização. 



Antes do JSON era muito comum o uso do XML, mais verboso e com mais marcações. O JSON ganhou espaço por ser mais compacto e por mapear diretamente para estruturas de dados que as linguagens de programação já possuem, como arrays e objetos.
É importante diferenciar uma API de um sistema web tradicional. Em um sistema web tradicional, o servidor recebe a requisição, processa e devolve uma página HTML já pronta, com layout, textos e dados misturados, destinada a ser exibida em um navegador por uma pessoa. Já uma API devolve apenas os dados, sem preocupação visual, e seu consumidor principal é outro programa. Isso permite que a mesma API alimente simultaneamente um site, um aplicativo móvel e um sistema parceiro, cada um apresentando as informações do seu jeito. Hoje é comum que os dois mundos se combinem: o front-end (feito em JavaScript, por exemplo) consome a API do back-end e monta a tela no navegador, em vez de o servidor entregar o HTML completo.

Em projetos reais, costuma-se usar um framework como Laravel ou Symfony, que oferece roteamento, validação, autenticação e tratamento de erros prontos, mas o princípio é o mesmo: receber, validar, processar e responder em formato padronizado.
Quando uma API expõe dados de uma empresa, a segurança deixa de ser opcional. É preciso distinguir autenticação, autorização e proteção geral. A autenticação responde à pergunta “quem é você?” e costuma ser feita por chaves de API (API keys), tokens JWT ou pelo protocolo OAuth 2.0, que permite a um sistema acessar dados em nome de um usuário sem conhecer sua senha. A autorização responde “o que você pode fazer?”, ou seja, mesmo autenticado, um cliente só deve acessar os recursos e executar as operações permitidas ao seu perfil, e uma falha nesse ponto (como permitir que um usuário consulte pedidos de outro apenas trocando o número na URL) é um dos problemas mais comuns apontados pelo projeto OWASP. Além disso, toda comunicação deve ocorrer por HTTPS para que dados e credenciais não trafeguem em texto aberto. Recomenda-se ainda validar e filtrar tudo o que chega, usar consultas parametrizadas para evitar SQL Injection, limitar o número de requisições por cliente (rate limiting) para reduzir abusos, não expor mensagens de erro com detalhes internos, guardar tokens e senhas em variáveis de ambiente em vez de deixá-los no código e registrar os acessos em logs para auditoria.
No ambiente empresarial, as APIs aparecem em praticamente todos os setores. Lojas virtuais usam APIs de gateways de pagamento, como Mercado Pago e Stripe, para processar cartões e Pix sem armazenar dados sensíveis, e APIs de transportadoras para calcular fretes e rastrear entregas. Sistemas de gestão (ERP) e de relacionamento com o cliente (CRM) trocam informações de vendas, estoque e financeiro por meio de APIs. Empresas emitem notas fiscais eletrônicas integrando-se a serviços fiscais, consultam CEPs e CNPJs em bases públicas como a ViaCEP e a BrasilAPI e enviam mensagens por serviços de e-mail, SMS ou WhatsApp. Bancos, por meio do Open Finance, compartilham dados de clientes entre instituições, com consentimento, também por APIs. Em todos esses casos, o ganho é o mesmo: automatizar processos, reduzir retrabalho e permitir que cada sistema se concentre no que faz de melhor.
